# Reglas del Proyecto — Ecommerce

> Este archivo define los tres pilares de gobernanza del proyecto:
> la jerarquía de agentes, la Regla de Espejo y el Ciclo SDD.

---

## 1. Jerarquía de Agentes

Cada agente opera dentro de un dominio exclusivo. Cruzar fronteras está **prohibido** salvo coordinación explícita vía handoff.

| Rol | Agente | Dominio (Scope) | Restricciones | Regla de Ejecución |
|-----|--------|-----------------|---------------|---------------------|
| **Orchestrator** | @Orchestrator_Agent | `.specs/`, `.context/handoffs/`, `project_manifest.md` | NO escribe código de producción. NO toca apps Django (`accounts/`, `productos/`, `ordenes/`, `carrito/`, `core/`) ni `templates/`, `static/` | Planifica, delega y cierra features. Único punto de entrada para nuevas tareas. |
| **Architect** | @Architect_Agent | `.specs/`, `project_manifest.md` | NO escribe código. NO toca apps Django, `templates/`, `static/`, `docker-compose.yml`, `Dockerfile` | Audita planes y diseños. Veta propuestas que violen el manifiesto. |
| **Backend** | @Backend_Agent | `accounts/`, `productos/`, `ordenes/`, `carrito/`, `core/`, `config/`, `manage.py` | NO toca `templates/`, `static/` ni `docker-compose.yml`, `Dockerfile` | SDD: lee spec → propone estructura → espera aprobación → implementa. |
| **Frontend** | @Frontend_Agent | `templates/`, `static/` | NO toca apps Django (`accounts/`, `productos/`, etc.) ni `docker-compose.yml`, `Dockerfile` | SDD: lee spec → define interfaz → espera aprobación → implementa. |
| **DevOps** | @DevOps_Agent | `.infra/`, `docker-compose.yml`, `docker-compose.dev.yml`, `Dockerfile`, `Dockerfile.dev`, `nginx/` | NO altera lógica de negocio en apps Django ni en `templates/`, `static/` | Seguridad por Diseño. Gestiona contenedores, CI/CD, gateway y plantillas de infraestructura. |
| **Tester** | @Tester_Agent | `accounts/tests/`, `*/tests/`, `tests/` | NO modifica código de producción. Solo reporta fallos. | Escribe y ejecuta tests contra el `.spec.md`. No arregla código. |
| **Docs** | @Docs_Agent | `project_manifest.md`, `docs/`, `README.md` | NO escribe código de producción. | Mantiene documentación sincronizada con el estado real del proyecto. |

### Regla Crítica — Handoff Obligatorio

> **Todo agente**, al completar CUALQUIER acción, **DEBE** emitir un HANDOFF de tipo
> `COMPLETION` dirigido a `@Orchestrator_Agent` siguiendo la plantilla en
> `.context/handoffs/_template.md`. Sin handoff = trabajo no registrado.

## 2. Regla de Espejo (Mirror Rule)

> **La estructura de archivos Markdown DEBE reflejar fielmente la arquitectura real del sistema, y viceversa.**

### Principio

Existe una correspondencia 1:1 entre la documentación en `.specs/` y los componentes reales del sistema. Cuando uno cambia, el otro **debe** actualizarse en el mismo ciclo.

### Implicaciones Prácticas

- **Nuevo módulo en el código** → Debe existir (o actualizarse) un `.spec.md` que lo describa.
- **Nuevo `.spec.md`** → Debe corresponder a un componente planificado o existente en el código.
- **Eliminación de un componente** → El `.spec.md` asociado se marca como `DEPRECATED` o se archiva.
- **Cambio en la arquitectura** → El `project_manifest.md` se actualiza para reflejar el nuevo estado.

### Verificación

El @Architect_Agent es responsable de auditar la consistencia entre specs y código. Cualquier desviación detectada genera un HANDOFF de tipo `BLOCKER` hacia @Orchestrator_Agent.

## 3. Ciclo SDD (Spec Driven Development)

Todo el desarrollo sigue un flujo de 7 fases secuenciales. **Ningún agente escribe código sin un `.spec.md` aprobado.**

```
Explore → Propose → Design → Spec → Tasks → Apply → Verify
```

### Fase 1: Explore (Explorar)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Comprender el problema, el contexto y las restricciones antes de proponer soluciones. |
| **Agente líder** | @Orchestrator_Agent |
| **Actividades** | Recopilar requisitos del usuario, analizar el estado actual del `project_manifest.md`, identificar dependencias y riesgos. |
| **Entregable** | Documento de contexto con problema definido, restricciones identificadas y alcance preliminar. |

### Fase 2: Propose (Proponer)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Presentar una propuesta de solución de alto nivel para validación. |
| **Agente líder** | @Orchestrator_Agent |
| **Actividades** | Redactar propuesta con enfoque técnico, alternativas consideradas y justificación de la solución elegida. |
| **Entregable** | Propuesta de feature con alcance, impacto estimado y dependencias. |

### Fase 3: Design (Diseñar)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Definir la arquitectura técnica detallada de la solución propuesta. |
| **Agente líder** | @Architect_Agent |
| **Actividades** | Diseñar contratos de API, modelos de datos, diagramas de flujo y definir restricciones técnicas. Auditar que el diseño no viole el manifiesto. |
| **Entregable** | Documento de diseño técnico con contratos, modelos y diagramas. |

### Fase 4: Spec (Especificar)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Formalizar la solución en un `.spec.md` con criterios de aceptación verificables. |
| **Agente líder** | @Architect_Agent |
| **Actividades** | Redactar el spec usando `template_feature.md`. Incluir: Objetivo, Contratos de API, Modelo de Datos, Criterios de Aceptación (DoD), Dependencias, Constraints y Contexto Mínimo. |
| **Entregable** | Archivo `.spec.md` aprobado en `.specs/features/`. |

### Fase 5: Tasks (Planificar Tareas)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Descomponer el spec en subtareas asignables con orden de ejecución claro. |
| **Agente líder** | @Orchestrator_Agent |
| **Actividades** | Generar Action Plan usando `template_task.md`. Asignar cada subtarea a un agente específico. Definir dependencias entre pasos y DoD por subtarea. Enviar a @Architect_Agent para auditoría. |
| **Entregable** | Action Plan auditado y aprobado en `.specs/tasks/`. |

### Fase 6: Apply (Implementar)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Ejecutar las subtareas del Action Plan respetando las fronteras de dominio. |
| **Agente líder** | Agente asignado por subtarea (@Backend_Agent, @Frontend_Agent, @DevOps_Agent, etc.) |
| **Actividades** | Cada agente lee su subtarea, implementa la solución dentro de su dominio exclusivo y emite un HANDOFF de tipo `COMPLETION` al finalizar. |
| **Entregable** | Código implementado + HANDOFF de completion por cada subtarea. |

### Fase 7: Verify (Verificar)

| Campo | Detalle |
|-------|---------|
| **Objetivo** | Validar que la implementación cumple todos los criterios de aceptación del spec. |
| **Agente líder** | @Tester_Agent |
| **Actividades** | Ejecutar tests contra los criterios del `.spec.md`. Reportar resultados. Si hay fallos, emitir HANDOFF de tipo `BLOCKER`. @Orchestrator_Agent actualiza el `project_manifest.md` al completar. |
| **Entregable** | Reporte de tests + actualización del estado en el manifiesto (DONE o BLOCKED). |
