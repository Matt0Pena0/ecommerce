# Security Checklist — Ecommerce

> Este archivo define los patrones y procedimientos para garantizar que el repositorio
> del proyecto **Ecommerce** no contenga secretos, credenciales ni datos sensibles
> versionados. Debe validarse antes de cada commit y como parte del proceso de CI/CD.
>
> Responsable: @DevOps_Agent (auditoría) — Todos los agentes lo aplican en su dominio.

---

## 1. Datos Sensibles que NUNCA se Versionan

Las siguientes categorías de datos **nunca** deben aparecer en archivos versionados del
repositorio. Si necesitan existir, van en `.env` / `.env.prod` (ignorados por Git).

### 1.1 Secretos de Django

| Dato sensible | Dónde debe ir | Nunca en |
|---------------|---------------|----------|
| `SECRET_KEY` | Variable de entorno (`.env`) | `settings/*.py`, código |
| Credenciales de base de datos (`DB_USER`, `DB_PASS`, `DB_ROOT_PASSWORD`) | `.env` / `.env.prod` | `docker-compose.yml`, `settings/*.py` |
| Credenciales SMTP (`EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`) | `.env` / `.env.prod` | código, templates |
| `ALLOWED_HOSTS` de producción | `.env.prod` | hardcodeado en base.py |

### 1.2 Base de Datos y Fixtures

| Riesgo | Recomendación |
|--------|---------------|
| Dumps de producción con datos reales de usuarios | No versionar. `data/*` ya está en `.gitignore`. |
| Fixtures con emails/direcciones reales | Usar datos ficticios en fixtures versionados. |
| `db.sqlite3` | Ya ignorado en `.gitignore`. |

### 1.3 Integraciones de Terceros

| Dato sensible | Dónde debe ir |
|---------------|---------------|
| API keys de pasarelas de pago | `.env` / `.env.prod` |
| Tokens de servicios externos | `.env` / `.env.prod` |
| Credenciales de storage (S3, etc.) | `.env` / `.env.prod` |

---

## 2. Patrones Regex Prohibidos

Los siguientes patrones detectan secretos y credenciales que **nunca** deben estar
presentes en archivos versionados del repositorio.

| Patrón Regex | Descripción |
|--------------|-------------|
| `SECRET_KEY\s*=\s*['\"][^'\"]+['\"]` | SECRET_KEY de Django hardcodeada |
| `mysql://.*:.*@` | Connection strings de MySQL con credenciales |
| `redis://.*:.*@` | Connection strings de Redis con credenciales |
| `(sk_live_\|pk_live_\|sk_test_\|pk_test_).*` | Payment keys (Stripe u otros) |
| `-----BEGIN (RSA\|EC\|DSA)? ?PRIVATE KEY-----` | Claves privadas |
| `ghp_[A-Za-z0-9]{36}` | GitHub Personal Access Tokens |
| `AKIA[0-9A-Z]{16}` | AWS Access Key IDs |
| `password\s*=\s*['\"][^'\"]+['\"]` | Passwords hardcodeados |

---

## 3. Comandos de Verificación

Ejecutar desde la raíz del repositorio antes de cada commit:

```bash
# SECRET_KEY hardcodeada en settings o código
grep -rn -E "SECRET_KEY\s*=\s*['\"][^'\"]+['\"]" --include="*.py" .

# Connection strings con credenciales embebidas
grep -rn -E "(mysql|redis)://.*:.*@" .

# Payment keys y claves privadas
grep -rn -E "(sk_live_|pk_live_|sk_test_|pk_test_)" .
grep -rn -E "-----BEGIN.*PRIVATE KEY-----" .

# Tokens de terceros
grep -rn -E "(ghp_[A-Za-z0-9]{36}|AKIA[0-9A-Z]{16})" .

# Verificar que los archivos .env NO estén trackeados por Git
git ls-files | grep -E "\.env($|\.)"
```

> **Resultado esperado**: Cero coincidencias en todos los comandos. Cualquier coincidencia
> indica una posible fuga de credenciales que debe corregirse antes de commitear.

---

## 4. Procedimiento de Corrección

Cuando se detecta un secreto versionado, seguir estos pasos:

### Paso 1 — Identificar

Ejecutar el `grep` correspondiente y anotar archivo, línea y contenido de la violación.

### Paso 2 — Externalizar el secreto

Mover el valor a `.env` / `.env.prod` y leerlo con `python-decouple`:

```python
# ANTES (violación):
SECRET_KEY = "django-insecure-abc123..."

# DESPUÉS (corregido):
from decouple import config
SECRET_KEY = config("SECRET_KEY")
```

### Paso 3 — Rotar la credencial

Si el secreto ya fue commiteado y pusheado, **rotarlo** (generar uno nuevo). El historial
de Git conserva el valor antiguo, por lo que ya no es seguro.

### Paso 4 — Verificar

Reejecutar los comandos de la Sección 3 y confirmar cero coincidencias.

---

## 5. Checklist de Validación Pre-Commit

Antes de cada commit:

- [ ] Ejecutar los comandos `grep` de la Sección 3
- [ ] Confirmar que `.env`, `.env.dev`, `.env.prod` NO están trackeados (`git ls-files`)
- [ ] Verificar que no hay `SECRET_KEY`, passwords ni API keys hardcodeados
- [ ] Confirmar que los dumps/fixtures no contienen datos reales de usuarios
- [ ] Confirmar cero coincidencias en todos los comandos de verificación
